## Гипотеза отличия (до кода)

В основном проекте AICM Nautilus уже пробовали — нужных результатов не дал. Логов той попытки в лаборатории нет. Корневая причина неизвестна: не адаптер, не live vs backtest, не данные, не производительность, не API — ни одно из этого не установлено. Угадывать запрещено. Домом исполнения Nautilus здесь не станет. Именованный эксперимент только: replay-only, каталог данных, не live, не Bitget-бот.

Отличие, которое мы можем проверить без логов той попытки: не «почему там упало» (неизвестно), а «здесь Nautilus не дом и не live, а только детерминированный replay по локальному каталогу баров K-0, и его baseline-метрики совпадают с каркасом K-0».

> **K-1 не стартовать, сначала K-0.**

Различие с упавшей попыткой в основном проекте **неверифицируемо** без тех логов; отказываемся гадать. Независимо от этого критерий успеха K-1 — прогон *против baseline K-0*, значит сначала должны существовать каталог K-0 и отчёт Tester (цифры с реального прогона, не из этой спецификации). Пока их нет, этот файл — **припаркованная спецификация**, не наряд на установку и не наряд на код.

### Проверяемая гипотеза — только если у K-0 есть реальный отчёт Tester

Условие активации H1: отчёт Tester K-0 с числами прогона (окно, n_bars, return, max DD), не формулировки этого файла.

**H1.** `BacktestNode` / catalog replay той же серии BTCUSDT 1h даёт то же окно, то же число баров, тот же buy&hold return, тот же buy&hold max DD и no-trade 0/0, что и отчёт K-0, в заявленной толерантности: точное совпадение `n_bars` и окна; return/DD равны округлению той же формулы.

- Если H1 не держится: не «настраивать» Nautilus в дом исполнения; зафиксировать расхождение и рассматривать K-1b.
- Если H1 держится: Nautilus — *заменяемый replay-субстрат*, по-прежнему не дом исполнения.

Числа P&L / DD / n_bars в этот файл не вписываются: прогона K-0 ещё нет.

### Что docs реально говорят про ядро, каталог, replay

Из README: Rust-native engine; research, детерминированная симуляция и live execution в **одной event-driven архитектуре**. Те же execution semantics и детерминированная модель времени в research и live.

Из architecture (latest): контексты `Backtest` (исторические данные, симулированное исполнение), `Sandbox`, `Live`. Backtest, sandbox и live **разделяют** `NautilusKernel`. Event-driven; данные в бэктесте упорядочиваются, ядро однопоточное — детерминированный порядок событий.

Из concepts/data (latest = nightly по содержанию каталога, оба 200):

- Поддерживаются bars / ticks / quotes / order book и др.; общие концепции для backtesting, sandbox и live.
- «From the DataEngine onward, data follows the same pathway regardless of environment context (backtest, sandbox, live).»
- Бэктест: данные упорядочены по `ts_init` стабильной сортировкой — «This ordering gives backtests deterministic replay.»
- **Данные в движок не прилагаются:** внешние записи нужно конвертировать в объекты модели NautilusTrader *до* добавления в бэктест или записи в каталог.
- Каталог: «The data catalog stores NautilusTrader data in Parquet files for backtesting, live trading, and research.»
- Имя API: **`ParquetDataCatalog`** (`from nautilus_trader.persistence import ParquetDataCatalog`) — Python-интерфейс к Rust-каталогу и DataFusion. Пишет/читает Parquet (бары, тики, котировки, стакан и др.). Локальный путь или object-store URI.
- `BacktestDataConfig` задаёт, что `BacktestNode` грузит из каталога на один прогон (`data_type` в т.ч. `Bar`; `catalog_path`; `instrument_id` / `bar_types`; опциональные UNIX-ns границы).
- Загрузка прогона: создать `ParquetDataCatalog` из конфига → инструменты → запрос DataFusion → сортировка merged data по `ts_init` → в backtest engine.
- `LiveNodeConfig` **не** принимает конфигурацию каталога; исторические данные в live — через data client или прямой запрос каталога. Для K-1 live-узел не используется.
- High-level API: `BacktestNode` — config-driven backtesting с Parquet-каталогом; «processes all data in timestamp order with deterministic execution semantics». Документ также говорит, что те же паттерны несут в live через `LiveNode` — это свойство движка, **не** цель K-1.

Итого для контура: event-driven ядро на research/backtest/live; каталог баров/тиков в Parquet; данные грузим мы. Live и venue-адаптеры исполнения в K-1 выключены нашим скоупом, не потому что «там упало».

## Механизм (когда ворота сняты)

Только после реального отчёта Tester K-0. Не Python-tutorial.

- **Вход:** локальный каталог баров, который произведёт K-0 (`/workspace/aicm/data/binance-vision/BTCUSDT/1h/` или путь, который определит K-0). Не yfinance, не FRED, не Stooq, не ключи бирж, не Bitget.
- **Загрузка:** конвертация наших баров в модель Nautilus → запись в `ParquetDataCatalog` (официальное имя API на 2026-08-30) → `BacktestDataConfig` / `BacktestRunConfig`.
- **Прогон:** только replay / `BacktestNode`. Нет `LiveNode`. Нет venue-адаптеров исполнения. Нет API-ключей.
- **Стратегия внутри прогона:** те же два baseline, что K-0 — buy&hold и no-trade. Нет волновых/новостных входов. Слои Андреев / Радченко / Миша / TE / Zatulyviter / Армен / Антон не клеить.
- **Выход:** отчёт против метрик K-0. Те же определения: окно, n_bars, return, max DD.
- **Роль:** Nautilus не дом. Если H1 держится — субстрат, который позже можно сменить (LEAN / тоньше). Если нет — не удваивать ставку в live-адаптеры.

Установка только после снятия ворот K-0; не в GitHub.
