### L2-B2 — Capability Identity, Hierarchy and Proof (`AICM-L2-PREF-034`–`070`)

### `AICM-L2-PREF-034` — AICM-owned durable Capability identity
- fidelity: verbatim
- источник: `12_SESSION_17_DECISION_REGISTER.md` §4; `02_…PREFERENCE_DRAFT_v0.1.md` §14 Confirmed preference map
- текст: **Status:** CONFIRMED. **Decision:** A Capability is a durable AICM semantic identity for an ability to produce a bounded outcome or effect; it is not owned by a model, provider, agent, prompt, service, container, deployment or session. **Boundary:** A realization may provide, host or expose a Capability but cannot redefine or erase its identity by replacement or failure.
  - **расширение draft:**
    Architecture theorem (draft §3):

    ```text
    Capability identity
    != provider / model / agent / prompt / service / container / runtime
    != proof product
    != current disposition
    != consumer enrollment
    != authority
    ```

    AICM owns the semantic identity. Providers realize it. Evidence assesses it. A current disposition describes it. Consumer Enrollment permits bounded use. External authority permits consequences.

    Core object identities (draft §4):

    | Object | Meaning | Does not imply |
    |---|---|---|
    | Capability Lineage | durable identity of one semantic ability | current proof or provider |
    | Capability Contract Edition | exact immutable semantic contract | implementation schema |
    | Provider Enrollment | realization currently eligible to provide | Capability validation |
    | Capability Claim | assertion that an ability exists/is needed | Candidate or proof |
    | Capability Candidate | admitted subject of assessment | validated status |
    | Capability Assessment | bounded evaluation activity/product | final disposition |
    | Capability Evidence Corpus | exact evidence and relations | one summary verdict |
    | Capability Proof Product | scoped synthesis over a sealed cut | universal truth/authority |
    | Current Capability Disposition | current bounded semantic status | operational use |
    | Consumer Enrollment | bounded permission/contract for one consumer | global Capability status |
    | Capability Use View | purpose-bound retrieval of current state | authority expansion |

### `AICM-L2-PREF-035` — Capability identity invariants and semantic contract

### `AICM-L2-PREF-042` — Atomic Capability identity
- fidelity: verbatim
- источник: `12_SESSION_17_DECISION_REGISTER.md` §4; `02_…PREFERENCE_DRAFT_v0.1.md` §14 Confirmed preference map
- текст: **Status:** CONFIRMED. **Decision:** An Atomic Capability is the smallest separately meaningful and independently assessable semantic ability within the current architecture, not necessarily the smallest software component. **Boundary:** Atomicity is semantic and assessment-relative; it does not imply one model, one process or one container.
  - **расширение draft:**
    Hierarchy (draft §6):

    - **Atomic Capability:** smallest separately meaningful and independently assessable ability in the current semantic architecture.
    - **Composite Capability:** own contract delivered through explicit composition of other Capabilities and coordination conditions.
    - **System Capability:** AICM-wide ability whose proof includes cross-component coordination, continuity, authority and system invariants.
    - **Consumer-facing Projection:** view of one Capability for a consumer and purpose; not a new hierarchy class.

    Proof and authority never inherit automatically through the hierarchy.

    Guardrail 06 (подтверждённый strengthening, не отдельный PREF ID):

    Purpose: Provide one durable semantic mechanism for declaring, challenging, monitoring and propagating material dependencies across AICM without turning dependency analysis into topology, priority or authority.

    ```text
    HARD_PREREQUISITE

    CONFLICT
    INCOMPATIBLE
    TEMPORARY_BRIDGE
    DERIVED
    BLOCKING_CONDITION
    EVIDENCE_DEPENDENCY
    SUCCESSOR_BRIDGE
    ```

    - Capability → Capability;

    - Program → Capability Enrollment;

    - object → constraint, obligation or authority;
    - object → data/right/credential/resource/external act;
    - recovery and successor continuity.

    Correction, restriction, degradation, suspension, expiry, retirement, revival, successor and deletion are non-interchangeable. Past decisions and outcomes retain the exact dependency edition actually used.

    Inside standing authority the system may detect, validate, revalidate, restrict, replace and reconcile dependencies without routine Owner approval. Irreducible external rights/resources/actions use the established External Enabler contract and automatic resume.
