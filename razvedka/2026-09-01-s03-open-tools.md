### A) Идентичность / присутствие агентов

#### S03-A-01. A2A Agent Card — манифест присутствия, не личность системы

- **Имя.** Agent2Agent (A2A) Agent Card
- **URL.** https://a2a-protocol.org/v1.0.0/specification/ — доступ 2026-09-01. Релиз: https://a2a-protocol.org/latest/blog/2026/03/12/a2a-protocol-ships-v10-production-ready-standard-for-agent-to-agent-communication/ — доступ 2026-09-01. Репозиторий (лицензия): https://github.com/a2aproject/A2A — доступ 2026-09-01. Тег: https://github.com/a2aproject/A2A/releases/tag/v1.0.0 — доступ 2026-09-01.
- **Лицензия.** Apache License 2.0 (badge/текст репозитория a2aproject/A2A).
- **OSS / SaaS.** OSS-спека (Linux Foundation; TSC: AWS, Cisco, Google, IBM Research, Microsoft, Salesforce, SAP, ServiceNow).
- **Факт 2026.** v1.0.0 опубликован **2026-03-12** (git tag `Published: 2026-03-12T16:34:41Z`; блог того же дня: «first stable, production-ready version»). Linux Foundation press **2026-04-09**: one-year mark, 150+ организаций.
- **Что это.** JSON-манифест A2A Server: `name`, `description`, `version`, `supportedInterfaces` (url + protocolBinding + protocolVersion), `capabilities`, `skills`, `securitySchemes`, опционально `iconUrl`. Клиент открывает карточку до сессии. Спека прямо: Agent Card = metadata identity/capabilities/skills/endpoint/auth — **не** внутреннее состояние, память или tools агента (opaque execution). Well-known путь в примерах spec: `GET /.well-known/agent-card.json`. Норматив: `spec/a2a.proto`.
- **Для чего в AICM.** Карточка **роли** (Разведчик, Канонист…) как объявление skills/интерфейса внутри одного контейнера — не 8 микросервисов и не «AICM = Google A2A». Картограф читает карточки; штаб не путает карточку с каноном.
- **Копируемо | адаптируемо | не брать.** *Адаптируемо:* форма манифеста роли (имя, skills, режимы ввода/вывода, auth). *Не брать:* A2A как идентичность AICM; «агент = отдельный endpoint»; LangGraph/CrewAI «теперь работают вместе» из press как приглашение ставить фреймворки.

#### S03-A-02. Extended Agent Card — progressive disclosure присутствия

- **Имя.** Get Extended Agent Card (`AgentCard.capabilities.extendedAgentCard`)
- **URL.** https://a2a-protocol.org/v1.0.0/specification/ §3.1.11, §4.4.3 — доступ 2026-09-01.
- **Лицензия.** Apache 2.0 (тот же протокол).
- **OSS / SaaS.** OSS-спека.
- **Факт 2026.** Поле перенесено в `AgentCapabilities` в релизе v1.0.0 (**2026-03-12**, changelog tag: `Move extendedAgentCard field to AgentCapabilities` #1307). Публичная карточка vs authenticated extended — норма spec, не маркетинг.
- **Что это.** Если `capabilities.extendedAgentCard: true`, после auth клиент вызывает Get Extended Agent Card и **заменяет кэш** публичной карточки на расширенную (доп. skills) на время сессии. Без флага — `UnsupportedOperationError`. Объявили, но не настроили — `ExtendedAgentCardNotConfiguredError`.
- **Для чего в AICM.** Мир уже умеет несколько проекций (S02 закрыто): публичное присутствие роли ≠ полный пакет в `razvedka/`. Drill-down идентичности по auth/scope, не reopen L0–L2.
- **Копируемо | адаптируемо | не брать.** *Копируемо как идея disclosure:* публичный ярлык роли / расширенный пакет. *Не брать:* Owner-as-operator на каждый extended fetch; склеивать extended card с PREF.

#### S03-A-03. Signed Agent Card — JWS на ключ, не «кто это»

- **Имя.** `AgentCardSignature` (JWS / RFC 7515)
- **URL.** https://a2a-protocol.org/v1.0.0/specification/ §4.4.7 — доступ 2026-09-01. Анонс v1.0: «Signed Agent Cards provide cryptographic verification of agent identity and metadata» — https://a2a-protocol.org/latest/blog/2026/03/12/a2a-protocol-ships-v10-production-ready-standard-for-agent-to-agent-communication/ — доступ 2026-09-01.
- **Лицензия.** Apache 2.0.
- **OSS / SaaS.** OSS-спека.
- **Факт 2026.** Поле `signatures` в AgentCard v1.0 (**2026-03-12**). Спека: объект = `protected` + `signature` + optional `header` (JWS). Спека **не** задаёт PKI «ключ = юридическое лицо / Owner».
- **Что это.** Подпись карточки ключом. Анонс говорит «verification of agent identity»; нормативный текст говорит: JWS над AgentCard. Это **продуктовый маркетинг vs spec**: подпись доказывает держателя ключа, не привязку ключа к человеку/организации внутри A2A.
- **Для чего в AICM.** Не путать криптографическую целость манифеста роли с каноном и не звать Owner «подписать личность системы». Канонист не кладёт канон в JWS карточки.
- **Копируемо | адаптируемо | не брать.** *Адаптируемо:* целостность файла манифеста роли. *Не брать:* Signed Card как Foundation-идентичность AICM; registry «AgentID» вне spec как будто он уже в A2A.

#### S03-A-04. MCP Apps — UI-присутствие инструмента, не идентичность хоста

- **Имя.** MCP Apps (SEP-1865) / `ui://` resources
- **URL.** https://modelcontextprotocol.org/seps/1865-mcp-apps-interactive-user-interfaces-for-mcp — доступ 2026-09-01. Спека расширения: https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx — доступ 2026-09-01 (сниппет WebSearch + SEP).
- **Лицензия.** Расширение открытого MCP; SPDX файла spec в этой сессии **не найден** отдельно от MCP (не выдумывать). Протокол MCP — открытый стандарт (не переписывать 2026-07-28).
- **OSS / SaaS.** OSS-расширение протокола (optional). Хосты — разные (SaaS/IDE).
- **Факт 2026.** Спека датирована **2026-01-26** (`specification/2026-01-26/apps.mdx`). SEP-1865 Created **2025-11-21**, Status **Final**. Примитивы: `ui://`, `_meta.ui`, capability `"io.modelcontextprotocol/ui"`, MIME `text/html;profile=mcp-app`, iframe sandbox, JSON-RPC `ui/*`.
- **Что это.** Сервер отдаёт интерактивный HTML в песочнице хоста. Это **поверхность присутствия инструмента** внутри чата/IDE, не «MCP = AICM». Согласование capabilities обязано быть явным. Кросс-реф: QE-C-03/04 = tools/elicitation как вопросник полномочий; здесь — UI как виджет, не новый опросник.
- **Для чего в AICM.** Виджет роли/пакета в viewport (Картограф), без превращения MCP-хоста в личность системы. Порт остаётся портом (LC-13/14).
- **Копируемо | адаптируемо | не брать.** *Адаптируемо:* песочничный виджет поверх tool result. *Не брать:* MCP Apps как identity AICM; HITL-оператора на каждый UI tool call как роль; Typeform/Listen MCP из QE-A как дом присутствия.
